# 架构与设计

## 要解决的问题

静态审计（tabby / CodeQL / SAST）能从代码里找出"可能是漏洞"的路径，但回答不了几个决定性的问题：

- **线上实际加载哪个版本？** 补丁生效没、依赖里的漏洞版本还在不在、是不是二开改过——源码仓库说了不算，加载进 JVM 的才算
- **运行时开关/配置是什么？** debug 开关、鉴权开关、环境变量注入的 key、动态加载的配置——静态看不到
- **filter 实际走哪条分支？** WAF / 鉴权 / 限流 filter 的分支由运行时配置和请求决定，静态只能看到所有分支的存在
- **污点真的流到 sink 了吗？** 静态的路径在运行时可能因配置、反射、动态代理不可达；反之静态觉得不可达的可能运行时可达

→ 静态误报多，且证不了"真实可达"。

常驻 IAST agent（DongTai）能在运行时追踪污点，但代价是改部署、长期 hook、字节码插桩开销、自身成为攻击面。对生产自查、对加固环境，太重。

**本项目填中间**：临时 attach 进真实 JVM，看完即走，零侵入，专做"实证确认"这一步。

## 设计哲学：零侵入

"零侵入"在这里不只是技术洁癖，是安全考量：

- **不常驻**：arthas agent 只在 attach 会话期间存在，退出即卸载。不长期 hook 生产 JVM、不持续插桩、无稳态性能开销
- **不改目标 pod**：路径 C 用 ephemeral container，不修改 Pod spec 的正式字段（ephemeralContainers 是临时字段，退出即清）；不打入镜像、不注入 sidecar、不动 init
- **影响面可控**：临时 attach 看完即走，最坏情况是 attach 期间的一次方法拦截开销，不会持续影响服务
- **可审计**：一次会话就是一次取证，脚本日志 + arthas 命令历史本身就是审计记录

代价是**不能做长期监控、不能自动追踪所有请求**——但漏洞验证多数是"确认这一个 sink 真的可达"的一次性取证，不需要长盯。

> 这个哲学决定了 [tunnel-server 的取舍](development.md#tunnel-server-为什么暂缓)：tunnel 的常驻 client 违背零侵入，残值只剩 Web UI，在零侵入约束下不划算。

## 三层架构

```
┌─────────────────────────────────────────────────────────┐
│  底座层  tools/fetch.sh                                   │
│  arthas 4.3.4 + 8 个 JDK（4 版本 × 2 架构），离线可用      │
│  sha256 + ELF 双确认，幂等可重跑                          │
└─────────────────────────────────────────────────────────┘
                          │ 装好底座
                          ▼
┌─────────────────────────────────────────────────────────┐
│  摸底层  tools/probe-k8s.sh                               │
│  对每个候选 pod 探 6 项加固条件                            │
│  → 输出 exec-direct / ephemeral-container / blocked      │
└─────────────────────────────────────────────────────────┘
                          │ 按结果选路
                          ▼
┌──────────────────────┬──────────────────────────────────┐
│  路径 A               │  路径 C                           │
│  attach-k8s.sh       │  attach-ephemeral.sh              │
│  kubectl exec        │  kubectl debug 临时容器            │
│  未加固/轻加固 pod    │  加固 pod 主力（distroless/JRE）   │
│  容器自己的 java      │  外部传匹配 JDK 进去跑             │
└──────────────────────┴──────────────────────────────────┘
                          │
                          ▼
                 arthas 控制台 → 漏洞验证
```

三层各自独立可单独跑，但正确流程是顺序的：**不摸底直接 attach 加固 pod 必失败**。probe 是前置必做。

## 为什么是"多版本 + 双架构 JDK"

不是炫技，是 attach 机制的硬约束（详见 [为什么需要多版本双架构](../Readme.md#为什么需要多版本--双架构-jdk)）：

- JDK 8 目标需 JDK 8 的 `tools.jar`（9+ 移除），跨版本 attach 失败
- JDK 17/21 模块化封装，attach 需 `--add-opens`，arthas 本身要跑在 17+ 上
- 传本地 JDK 进容器时架构必须等于节点架构

→ 8/11/17/21 × x64/aarch64 = 8 个 JDK 是覆盖主流 Spring Boot 的最小完备集。

## 在安全工作流里的位置

```
静态审计（上游）          本项目（实证）              修复（下游）
tabby / CodeQL    →    arthas watch/trace    →    redefine 打补丁验证
找出嫌疑路径            确认真实可达/可触发         确认补丁真生效
（误报多）              （运行时真相）             （jad 看真实加载的代码）
```

- **上游**：静态审计产出"怀疑清单"——哪些类/方法可能是漏洞
- **本项目**：逐条运行时实证——这条路径真的可达吗、污点真的到 sink 了吗、运行时开关是开是关
- **下游**：修复后用 `jad`/`sc -d` 确认线上加载的是补丁版本，用 `watch` 确认 sink 不再被触发

## 与同类工具对比

| 工具 | 类型 | 侵入性 | 能回答的问题 | 局限 |
|---|---|---|---|---|
| tabby | 静态污点（Soot/CPG） | 无 | "代码里有没有这条嫌疑路径" | 误报多，证不了运行时可达，看不到动态配置 |
| CodeQL | 静态语义分析 | 无 | "代码模式上是否符合漏洞特征" | 同上，且需查询规则 |
| DongTai | 运行时 IAST agent | 高（常驻插桩） | "这个请求的污点真流到 sink 了" | 改部署、长期 hook、自身攻击面，加固环境难装 |
| **本项目** | **运行时临时 attach** | **零（看完即走）** | **"线上真实加载的代码/配置/数据流是什么"** | 不长期监控、不自动追踪所有请求、需目标可 attach |

不是替代关系，是互补：tabby/CodeQL 找嫌疑 → 本项目实证 → DongTai 适合需要长期被动检测的场景（但侵入重）。

## 项目的真正技术含量

不是"会跑 arthas"——arthas 谁都会跑。是**在企业级加固环境下还能把 arthas 送进真实 JVM**：

distroless 无 shell、JRE-only 无 attach API、readOnlyRootFS 写不了 /tmp、非 root 读不了 /proc、`-XX:+DisableAttachMechanism` 应用层禁 attach、准入策略禁 exec/ephemeral……任何一条都让"用容器 java 跑 arthas"失效。

底座的核心价值是 **probe 摸底 → 选路 → 匹配版本架构 JDK 送进去**这条链。这条链怎么处理每一种加固，见 [加固场景处理](hardening.md)；链里每个脚本怎么跑，见 [脚本详解](scripts.md)。
